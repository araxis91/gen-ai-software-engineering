A transaction never moves through one mind — it moves through four.

Every record in sample-transactions.json is inspected, risk-scored, compliance-checked, and settled by four independent agents that never call each other directly — they hand a file to whoever is configured to go next. Reorder the sequence and you change what the pipeline actually enforces.

Exhibit B — the pipeline
02 / 06

Four agents, four separate judgments

Each stage receives a transaction record, applies one rule, and either stamps it terminal or passes it on. None of them know what agent came before, and none of them decide who comes next — that decision belongs to the sequence, not the agent.

STAGE 1

Transaction Validator

Checks required fields are present, the amount is a positive number, and the currency is a real ISO 4217 code.

STAGE 4

Settlement Processor

Generates a settlement id and timestamp. Re‑running never double‑settles the same transaction.

Agents pass a TransactionRecord to each other through atomic file writes in shared/input → processing → output → results — the same discipline a real settlement network uses, so every intermediate state is a file you can open and read, not a value that only ever existed in memory.

Exhibit C — the sequence
03 / 06

The order is data, not code

A PipelineSequence — just an ordered list of agent names — is the only thing that decides what runs next. Reordering it, dropping a stage, or running one agent at a time changes what actually gets enforced, on purpose.

Default order
validator → fraud → compliance → settlement

TXN003's denylisted destination is caught by the compliance stage, third in line, after validation and fraud scoring already passed it through.

Compliance first
compliance → fraud → validator → settlement

Same rule, same catch — TXN003 is rejected immediately, first in line instead of third. Every agent still enforces its own rule correctly, wherever it sits.

Drop a stage entirely and its rule simply stops applying — a sequence of just validator → settlement means fraud scoring and compliance checks never run, and transactions that would normally be flagged or held settle instead. That's the trade-off the sequence makes explicit.

Exhibit D — entry points
04 / 06

Three ways in, one ledger

A transaction can arrive by batch file, HTTP request, or a question typed into an AI assistant — all three run the same agents and land in the same place.

Batch · file queue

CLI — Integrator

java … com.homework6.pipeline.Integrator

Loads the whole transactions file, drops one message per record into shared/input/, and runs the configured sequence over all of them.

Synchronous · HTTP

REST API — Spring Boot

POST /api/v1/transactions

Submits one transaction, runs it to completion in memory, and returns the terminal result in the same response — no polling required.

Conversational · MCP

Pipeline‑status server

get_transaction_status(id)

Lets an AI assistant answer "what happened to TXN003?" by reading the same result file — no separate database, no separate truth.

ALL THREE WRITE OR READ shared/results/*.json — one file per transaction, one shared source of truth

One command, zero manual steps

Exhibit F — verification
06 / 06

Proof, not promises

A claim about correctness is only as good as what checks it. Every rejection reason, every risk factor, and every routing decision has a dedicated test — and a hook that refuses to let unverified code leave the machine.

139 automated tests

Unit tests per agent and utility, plus full end-to-end tests that run real HTTP requests against a real embedded server into a temp shared/ directory.

80% the line a push cannot cross

A PreToolUse hook intercepts git push, runs the full suite, and blocks the push outright if coverage drops below this line.

91.8% actual line coverage

Comfortably clear of the gate, with the small remainder made up of defensive I/O error paths that are deliberately not chased for their own sake.
